# 微信排版与视觉复审

公众号沿用作者的完整内容与声音。先在 `polished.md` 修好语气和知识问题，再生成 `wechat.md`；不要靠公众号二次改写补救底稿。允许调整段落、加粗和图片位置，保留论证顺序、前提、代码、引用与真实材料。默认 90% 相似度只是粗筛，AI 仍需逐项检查事实覆盖。HTML 和 Markdown 须保持正文、数字、代码及图片一致，链接仅允许下文规定的编号引用呈现差异。

## 版式取舍

默认采用安静的单栏阅读版式：正文 16px、行高 1.85、段距 20px，左右内边距 16px；可按实际文章微调。主要文字 #333，辅助文字也须清楚可读。一级章节约 22px、二级 19px、三级 17px，标题上方留白大于下方；标题与加粗采用近黑色，强调色少量用于链接、引用编号和引用左边线；背景、代码块、表格与辅助文字保持中性。技术中英混排默认左对齐，避免两端对齐造成大空隙。以上是本插件的设计起点，不是平台强制参数。

排版前由 AI 根据全文的主要目的选择 `--article-type`，默认 `--theme auto` 映射如下：

| 文章类型 | 参数 | 主题与强调色 |
| --- | --- | --- |
| 技术教程、原理分析、工具实践 | `technical` | `blue`，克制的蓝色 `#285a91` |
| 工作复盘、成长经验、个人随笔 | `essay` | `warm`，暖棕 `#8a5036` |
| 旅行、居住、日常生活记录 | `lifestyle` | `sage`，灰绿 `#426657` |
| 综合内容、公告或类型不明确 | `neutral` | `neutral`，中性灰 `#505967` |

按读者来读这篇文章的主要目的判断，不按某个关键词机械分类。例如“程序员租房记”通常选生活类型，“三年工作复盘”通常选经验随笔；以解决技术问题为主、夹杂个人经历的文章仍选技术类型。用户指定配色优先，用 `--theme blue|warm|sage|neutral` 覆盖自动映射。旧的 `--theme ink` 继续可用，但不再默认采用。未提供类型时回退中性灰，不偷偷猜测。

在已有视觉复审说明里记录文章类型、最终主题及一句选择理由；HTML 的 `data-ymp-theme` 和 `data-ymp-article-type` 记录实际渲染选择。已有文章只在重新排版时更新，变更主题后重新生成截图。颜色只是区分气质的设计选择，不宣称某种颜色能提高阅读量；不能仅靠颜色表达章节层级、重点或链接身份。

不要把每段装进彩色卡片、不叠大边框或阴影，不用巨大编号占据首屏。正文保留内容本身的自然节奏，不强迫所有段落变成三行。

图片位置根据阅读需要决定：流程图放在流程引入之后，截图紧靠相应操作或结果，比较图放在比较判断附近。短引言、结尾、参考资料通常无需生成装饰图。不必在每个一级标题后立即放图，也不为填空生成无信息图片。正文首图可在导入段之后、第一个主章节之前；微信公众号列表封面仍是独立字段。原图全部保留，若同一图重复引用需核对是否承担不同作用。

代码采用可读等宽字体，保留缩进和字符；长行用视觉软换行或局部滚动，不能插入真实换行破坏复制。表格优先保留结构并控制列宽。过宽表格由 AI 在 Markdown 中改成同信息的分组条目，再同步生成 HTML，记录格式调整，不能截图后删掉唯一可复制数据。

## 可复用渲染

安装本 Skill 的 requirements.txt 后：

```bash
python3 <skill>/scripts/wechat_layout.py --input <project>/draft/wechat.md --output <project>/draft/wechat.html --article-type technical
python3 <skill>/scripts/wechat_preview.py --project-dir <project>
```

渲染器只负责排版，不改句子。支持标题、列表、引用、链接、图片、表格、行内与块代码。原始 HTML 先保真转成 Markdown；复杂数学、嵌套组件等由 AI 单独排版、预览和复核。也可以直接由 AI 编写行内 HTML，最后走同样验证，不以脚本主题限制设计。

预览器使用 Playwright Chromium（首次 `python3 -m playwright install chromium`），生成 375px、430px 截图与 `draft/preview/layout-evidence.json`。AI 必须打开实际截图检查：首屏是否进入主题、层级与留白是否清晰、图中文字是否可读、代码和表格是否越界、底部是否完整。`overflow` 或 `brokenImages` 非空时先修复。截图生成不会自动把复审记为 passed。

把实际观察说明、截图与 HTML 指纹写进 `editorial-review.json.wechat_layout`，见 editorial-review.md。改动 HTML 后重新截图并复审。微信实际编辑器会再次清洗样式，操作其草稿时再检查粘贴结果；本地预览不冒称平台效果已验证。

## 超链接：先让读者看懂，再处理平台呈现

链接文字用文章名、文档章节或具体用途，避免“这里”“点击查看”“链接”，也不要把整条带参数的 URL 当正文。链接名称不必复述文章完整长标题，但不能为了缩短改掉主题或夸大结论。URL 中的路径、参数、锚点必须原样保留；不要擅自删除访问令牌、必要查询参数或改用不明短链。

`wechat_layout.py` 默认 `--link-mode endnotes`：

- 普通 HTTP(S) 网页链接在原位置显示名称和小号编号，文末统一列出“名称 + 可复制完整地址”。相同 URL 只占一个编号；长 URL 只在参考区换行，不撑开正文。
- HTTPS 的 mp.weixin.qq.com/s 或 /s/... 文章地址保留可辨认的锚文本。不是看到域名字符串就放行，不能把仿冒域名当公众号文章。
- 已选历史博客也按同一方式处理。已有公众号同篇链接时先核实再加，不猜链接。
- 源 Markdown 仍保存标准链接。HTML 允许的差异仅是该确定性链接呈现：外链名称后的编号和文末地址；校验会独立生成期望呈现，拒绝删正文、改链接、丢编号或缺参考项。不是用较低相似度放过任意删改。
- 原有行内模式仍可用 `--link-mode inline`，适合已确认支持外链的目标环境。最终公众号草稿仍须核验实际跳转和样式清洗，不承诺所有账号能力一致。

新项目记录 `wechat_links_contract_version: 1`。正文出现裸网址或含糊链接文字时，CLI 和新项目校验会要求 AI 先命名。旧项目可添加该字段启用检查；渲染器默认均采用编号参考。只调整显示文字，不改目的地址；代码里的 URL、图片 src 与邮箱不当作普通文章链接替换。复杂 HTML 链接先保真整理成 Markdown，再采用同一规则。

## 让读者愿意继续读

- 首屏尽早出现具体问题与读者能得到的答案，避免封面后堆作者介绍、目录、重复大标题。导入段可以稍突出，但不新增一句泛泛的“本文将带你”。
- 小标题解释接下来要解决什么，维持层级差异；在论证转折处留白，不连续铺满同样大小的彩色卡片。
- 每段承担一个推进动作。按意思拆长段，不机械按手机行数截断；每节只强调真正关键的一两处，避免整段加粗和满屏强调色。
- 长说明中优先把真实步骤、截图或比较图放在读者需要的位置。短节宁可自然收束，不用装饰图或总结卡填空。
- 预览时从头连续读一遍，再检查链接密集段、超长链接、引用区、图片前后、表格和结尾。图看着好看不代表阅读过程清楚。
